# Архитектура и ключевые решения

Этот документ — не хронология (см. `docs/HISTORY.md`), а срез
текущего состояния: как устроен код и почему именно так. Обновлять
при значимых архитектурных изменениях.

## Философия проекта

- **Минимум зависимостей.** Весь HTTP — через stdlib `urllib`, вся
  БД — через stdlib `sqlite3`, входная точка — stdlib `http.server`
  (не Flask/FastAPI). Единственные внешние pip-пакеты — `tzdata`
  (нужна `zoneinfo` для часовых поясов с DST) — фиксируются точной
  версией (`==`), без диапазонов.
- **Вебхук, не long-polling.** Входящий трафик от Telegram не мешает
  Railway усыплять контейнер (Serverless); long-polling — постоянный
  исходящий трафик — не давал бы спать вообще.
- **Явные ошибки вместо тихого поведения.** Например: поиск не
  переключается автоматически на другой провайдер при пустом
  результате — это осознанный ответ, а не сбой, который нужно
  обходить (см. ниже).
- **Не гадать про сторонние API.** Была история с Keenable — угаданный
  формат оказался неверным (GET вместо POST, не тот заголовок).
  С тех пор — либо проверять по официальной документации/OpenAPI,
  либо честно предупреждать в коде и `.env.example`, что формат не
  подтверждён.

## Провайдеры: единый паттерн переключаемых бэкендов

Три независимые оси используют один и тот же приём — тонкий
диспетчер + активный выбор, сохранённый в таблице `settings`
(SQLite), переключаемый командой без передеплоя:

| Ось | Диспетчер | Команда |
|---|---|---|
| Поиск | `modules/search/service.py` | `/setsearch` |
| Модель | `llm/client.py` (`get_active_model`) | `/setmodel` |
| Провайдер LLM (ключ/base_url) | `llm/providers.py` | `/setprovider` |

Добавить новый поисковый провайдер — один файл в
`modules/search/providers/` с функцией
`search(query, max_results, **kwargs) -> list[dict]` в общем формате
`{"title", "url", "snippet"}`, плюс одна строка в `_PROVIDERS`.
Остального кода (`router`, `llm.orchestrator`) это не касается.

## Несколько LLM-провайдеров одновременно (`llm/providers.py`)

Профиль `default` — то, что в `.env` (`LLM_API_KEY`/`LLM_BASE_URL`/
`LLM_MODEL`), не хранится в SQLite повторно. Дополнительные профили
(`/addprovider`) — в `settings` как JSON. Активная модель запоминается
**отдельно на каждый профиль** (id модели одного провайдера обычно
бессмысленен для другого) — ключ `llm_model:<профиль>`.

Секьюрити-примечание: ключи доп. профилей живут в том же SQLite на
Railway Volume, что и всё остальное — тот же уровень защиты, что у
`.env` (доступ к volume = доступ к ключам, не больше и не меньше).

## Несколько пользователей — сознательно НЕ реализовано

Бот жёстко однопользовательский: `OWNER_CHAT_ID` проверяется в
`telegram/router.py` на каждое сообщение, все `settings` — глобальные
на весь бот, а не на пользователя. Чтобы пустить второго человека с
собственными настройками, потребуется:
- таблица пользователей с правами;
- все ключи `settings` (активный провайдер/модель/поиск и т.д.)
  переделать по образцу диалогов (`modules/conversations`) — с
  привязкой к `chat_id`, а не глобально;
- решить вопрос делимых лимитов (общие API-ключи = общий счётчик
  запросов и общий счёт);
- решить вопрос риска — например, доступ к `/pushcode`/`/editcode`
  от чужого имени в ваши репозитории.

Это отдельный шаг с отдельным обсуждением, не быстрая правка.

## Ветки диалогов (`modules/conversations/`)

Один `chat_id` может иметь несколько диалогов, у каждого своя история
и своя summary (`modules/memory/history.py`, `compactor.py` работают
по `conversation_id`, не по `chat_id`). Активный диалог на чат —
в `settings`. Самопамять (`self_memory`) — общая на все диалоги,
это то, что бот знает о себе/вас вообще, а не в рамках одной беседы.

Миграция для баз, созданных до этой возможности: старые сообщения и
summary автоматически переносятся в один "Перенесённый диалог" на
каждый `chat_id` при первом запуске нового кода — одноразово,
идемпотентно, ничего не теряется (`storage/db.py`:
`_backfill_conversations`).

## Поиск: retry и качество запроса

- **Retry на реальных ошибках** (`modules/search/service.py`) — один
  повтор через `SEARCH_RETRY_DELAY_SECONDS` (по умолчанию 2.5с),
  типичная причина — self-hosted SearxNG на Railway заснул
  (Serverless) и не ответил с первого раза. **Не** повторяется на
  `SearchConfigError` (нет ключа/URL) — такая ошибка не пройдёт и со
  второго раза.
- **Пустой результат ≠ ошибка.** Если поиск ничего не нашёл — бот
  честно отвечает "ничего не нашлось", **не** пробует автоматически
  другой провайдер. Осознанное решение: пустой результат часто
  означает, что в интернете действительно ничего релевантного нет;
  скрытый fallback добавил бы незаметные лишние запросы и мог бы
  маскировать проблемы конфигурации.
- **Уточнение запроса** (`llm/orchestrator.py`: `refine_query`) —
  отдельный лёгкий вызов LLM дочищает черновой запрос модели в
  компактный "поисковый" вид перед реальным поиском. Модель может
  запросить несколько разных запросов за один ответ (до
  `SEARCH_MAX_QUERIES_PER_TURN`) — что реально искалось, видно в
  ответе строкой `🔍 Искал: ...`.

## "Умное" определение бесплатных моделей (`llm/model_filter.py`)

Простая эвристика (`pricing.prompt == "0"`) не гарантированно
работает для всех провайдеров — например, у clavis.to цена может
лежать в нестандартном поле, для которого нет публичной документации
(риск повторить ошибку с Keenable). Вместо жёсткого парсинга под
каждого — компактные данные о цене (id + любые поля, похожие на цену
по названию) отдаются на анализ самой активной LLM, результат
кэшируется (`FREE_MODELS_CACHE_HOURS`). При сбое анализа — тихий
откат на эвристику.

## Дата и время в system-prompt

Вместо инструмента/round-trip'а (как для поиска) — текущие дата и
время (в `USER_TIMEZONE`) просто всегда подставляются в system-prompt
(`llm/prompts.py`) при каждом вызове. Это единственное значение,
которое сервер и так точно знает в момент запроса — незачем городить
отдельный механизм ради того, что можно отдать бесплатно и мгновенно.

## `/selftest` / `/selftest_all` vs `tests/test_all.py`

Это два разных инструмента с разной целью:
- **`tests/test_all.py`** — юнит-тесты корректности кода, всё внешнее
  (Telegram, LLM, поиск, GitHub) намеренно замокано, реальные ключи
  не нужны. Не проверяет, работает ли реальный деплой.
- **`/selftest`** (`modules/diagnostics/service.py`) — живая проверка
  прямо на сервере: по одному минимальному настоящему вызову к
  каждому настроенному сервису (база, LLM, поиск, GitHub-токен,
  мониторинг), с текущими ключами. Быстро.
- **`/selftest_all`** — то же самое плюс:
  - **Cron / напоминания** — ключевая диагностика для "напоминание не
    сработало": показывает возраст последнего реального тика Cron Job
    (по отметке `last_monitoring_report_at`, которую выставляет только
    `scheduler.run_tick`) и явно **падает с ошибкой**, если прямо
    сейчас есть просроченные, но недоставленные напоминания — это
    почти наверняка значит, что Railway Cron Job не настроен или не
    достукивается (неверный URL/секрет/расписание), а не что баг в
    самой логике напоминаний.
  - **Заметки и диалоги** — полный round-trip (создание → чтение →
    удаление/закрытие) под служебным `chat_id="_selftest"`, не
    трогает ваши настоящие данные.
  - **Список моделей** — реальный вызов к `{LLM_BASE_URL}/models`.
  - **GitHub round-trip** — по-настоящему создаёт ветку, коммитит
    файл, и удаляет ветку за собой — но только если задан
    `GITHUB_TEST_REPO` (отдельный тестовый репозиторий); без него эта
    проверка пропускается, чтобы `/selftest_all` не трогал рабочие
    репозитории без явного разрешения.

Оба стоят немного реальных денег/лимитов (LLM/поиск) — поэтому только
вручную, не по расписанию. `/selftest_all` дороже и дольше
`/selftest` — используйте его, когда нужно прогнать почти всё, а не
просто убедиться, что базовые интеграции живы.

## GitHub-навык: без клонирования репозитория

И `/pushcode` (Contents API, один файл — один коммит), и `/editcode`
(Git Data API: blob → tree → commit → обновление ref, несколько
файлов одним атомарным коммитом) работают только через GitHub REST
API — без `git clone` внутри контейнера, без временных файлов на
диске, без последующей очистки. `/editcode` читает текущее содержимое
файлов через тот же API, отдаёт модели, требует от неё **полное**
новое содержимое в строгом формате (`===FILE:===...===END===`) —
парсинг не зависит от того, какая именно модель отвечает.

Если ветка уже существует (продолжение правок несколькими вызовами
`/editcode`) — файлы читаются из неё же, а не из базовой, чтобы не
потерять предыдущие изменения.

## Длинные сообщения и лимит Telegram (4096 символов)

`telegram/api.py`: `MAX_MESSAGE_LENGTH = 3600` (запас под жёсткий
лимит Telegram в 4096) и `split_text_into_chunks()` — режет текст по
границе абзаца, потом по границе предложения, и только в крайнем
случае (одна гигантская "строка" без единого разделителя) — жёстко
посимвольно. `send_long_message()` шлёт получившиеся куски подряд,
с префиксом `[i/N]`, если кусков больше одного.

Где используется:
- **Обычный ответ LLM** (`_default_handler` в `telegram/router.py`) —
  всегда через `send_long_message`, без специального решения "резать
  или нет": если ответ короткий, это просто одно сообщение как раньше.
- **`/history`** — по умолчанию не режется, а **сжимается через LLM**
  (`llm/orchestrator.compress_text`) до `MAX_MESSAGE_LENGTH`, если не
  помещается: это связный текст переписки, есть смысл пересказать
  главное, а не обрубить на середине. Явная команда `/history
  полностью` — весь текст как есть, через `send_long_message`. При
  сбое LLM (или если она всё равно не уложилась в лимит) —
  `compress_text` откатывается на обычную обрезку по границе
  предложения, команда не перестаёт работать.
- **`/notes`** — по умолчанию просто обрезается по границе
  предложения/абзаца (`split_text_into_chunks(...)[0]`), **без**
  обращения к LLM — это список данных, а не текст для пересказа,
  сокращать "по смыслу" тут нечего. `/notes полностью` — все записи
  через `send_long_message`.

## Индикатор "печатает..." (пока без потокового вывода)

`telegram/router.py`: `_with_typing_indicator()` — оборачивает вызов
`orchestrator.get_reply()` в фоновый поток, который каждые 4 секунды
шлёт `sendChatAction(action="typing")` (сам индикатор в Telegram
гаснет примерно через 5с, поэтому нужно повторять, если ожидание
дольше), пока основной вызов не вернёт результат.

Настоящий потоковый вывод (стриминг токенов через многократные
`editMessageText`, как делают некоторые Telegram-боты) — пока не
реализован: это отдельная, более сложная переделка (нужно менять
`llm/client.py` на потребление streaming-ответа от API вместо
одного полного JSON, следить за собственным rate-limit'ом на
`editMessageText`, буферизовать частичный текст). Индикатор "печатает"
закрывает большую часть проблемы ("непонятно, зависло или работает")
намного дешевле — стриминг можно добавить отдельным шагом, если
станет действительно нужен.

## Самоосознание модели

`llm/prompts.py`: system-prompt явно говорит модели, что она работает
как часть личного Telegram-агента пользователя, через какого именно
провайдера/API и с какой моделью (`llm.providers.get_active_credentials()`
+ `llm.client.get_active_model()`) — так на вопрос "кто ты" или "на
чём ты работаешь" модель отвечает точно, а не гадает/выдумывает.
Меняется автоматически при `/setprovider`/`/setmodel` — блок всегда
описывает то, что активно прямо сейчас.

## Меню команд Telegram (`scripts/set_commands.py`)

Отдельный разовый скрипт (как `set_webhook.py`) — вызывает
`setMyCommands` с курируемым подмножеством самых частых команд (не
весь список — Telegram неудобно показывает длинные меню). Полный
список команд всегда доступен через `/help`. Запускать вручную после
изменения списка, не на каждом старте контейнера.

## Отказоустойчивость LLM (`llm/fallback.py`)

Если активная модель/провайдер прямо сейчас недоступны (модель
временно отключена, 5xx и т.п. — не ошибка конфигурации, ключ уже
проверен на этапе `/addprovider`), `resilient_chat_completion()`
пробует по очереди:
1. другие бесплатные модели ТОГО ЖЕ провайдера (через
   `llm/model_filter.py`);
2. другие настроенные профили провайдеров (порядок как в
   `/providers`) и их бесплатные модели.

Каждый профиль в системе по определению уже имеет свой ключ (его
нельзя добавить через `/addprovider` без `api_key`) — поэтому не
нужно отдельно проверять "стоит ли пробовать этот провайдер": раз
профиль есть, значит ключ для него есть.

Попытки **не меняют** `/setmodel`/`/setprovider` пользователя —
`llm/client.py: chat_completion()` принимает необязательные
`profile_name`/`model`, так что перебор идёт "мимо" настроек, не
переключая их. Если что-то из перебора сработало — это разовая
подмена только для этого конкретного ответа; в следующий раз бот
снова начнёт с настроенной по умолчанию модели (вдруг она уже
починилась).

Интеграция в `llm/orchestrator.py` — намеренно минимальная: один
импорт (`from llm.fallback import resilient_chat_completion_text as
chat_completion`) вместо `from llm.client import chat_completion`.
Вся остальная логика оркестратора (`get_reply`, `refine_query`,
`compress_text`, `summarize_history`) не изменилась ни на строку и
автоматически получила отказоустойчивость — `chat_completion(...)`
внутри них по-прежнему просто принимает messages и возвращает строку,
как и раньше. Это же значит, что и все побочные вызовы (уточнение
поискового запроса, сжатие истории, суммаризация) тоже пытаются
переключиться на резервную модель при сбое, не только основной ответ.

Лимитер запросов — свой на каждый профиль (`llm/client.py:
_get_limiter`), не общий: иначе исчерпанный лимит одного провайдера
мешал бы попытке fallback на другой, у которого лимит ещё есть.

Если сработал fallback — видно в логах контейнера (`profile_name`/
`model`, которые реально ответили), в сам ответ пользователю ничего
не добавляется (в отличие от `🔍 Искал:` для поиска — это осознанно,
чтобы не грузить каждую реплику служебными пометками; можно добавить
видимую пометку позже, если понадобится).
