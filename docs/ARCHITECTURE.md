# Архитектура и ключевые решения

Этот документ — не хронология (см. `docs/HISTORY.md`), а срез
текущего состояния: как устроен код и почему именно так. Обновлять
при значимых архитектурных изменениях.

## Философия проекта

- **Минимум зависимостей.** Весь HTTP — через stdlib `urllib`, вся
  БД — через stdlib `sqlite3`, входная точка — stdlib `http.server`
  (не Flask/FastAPI). Единственные внешние pip-пакеты — `tzdata`
  (нужна `zoneinfo` для часовых поясов с DST) — фиксируются точной
  версией (`==`), без диапазонов.
- **Вебхук, не long-polling.** Входящий трафик от Telegram не мешает
  Railway усыплять контейнер (Serverless); long-polling — постоянный
  исходящий трафик — не давал бы спать вообще.
- **Явные ошибки вместо тихого поведения.** Например: поиск не
  переключается автоматически на другой провайдер при пустом
  результате — это осознанный ответ, а не сбой, который нужно
  обходить (см. ниже).
- **Не гадать про сторонние API.** Была история с Keenable — угаданный
  формат оказался неверным (GET вместо POST, не тот заголовок).
  С тех пор — либо проверять по официальной документации/OpenAPI,
  либо честно предупреждать в коде и `.env.example`, что формат не
  подтверждён.

## Провайдеры: единый паттерн переключаемых бэкендов

Три независимые оси используют один и тот же приём — тонкий
диспетчер + активный выбор, сохранённый в таблице `settings`
(SQLite), переключаемый командой без передеплоя:

| Ось | Диспетчер | Команда |
|---|---|---|
| Поиск | `modules/search/service.py` | `/setsearch` |
| Модель | `llm/client.py` (`get_active_model`) | `/setmodel` |
| Провайдер LLM (ключ/base_url) | `llm/providers.py` | `/setprovider` |

Добавить новый поисковый провайдер — один файл в
`modules/search/providers/` с функцией
`search(query, max_results, **kwargs) -> list[dict]` в общем формате
`{"title", "url", "snippet"}`, плюс одна строка в `_PROVIDERS`.
Остального кода (`router`, `llm.orchestrator`) это не касается.

## Несколько LLM-провайдеров одновременно (`llm/providers.py`)

Профиль `default` — то, что в `.env` (`LLM_API_KEY`/`LLM_BASE_URL`/
`LLM_MODEL`), не хранится в SQLite повторно. Дополнительные профили
(`/addprovider`) — в `settings` как JSON. Активная модель запоминается
**отдельно на каждый профиль** (id модели одного провайдера обычно
бессмысленен для другого) — ключ `llm_model:<профиль>`.

Секьюрити-примечание: ключи доп. профилей живут в том же SQLite на
Railway Volume, что и всё остальное — тот же уровень защиты, что у
`.env` (доступ к volume = доступ к ключам, не больше и не меньше).

## Несколько пользователей — сознательно НЕ реализовано

Бот жёстко однопользовательский: `OWNER_CHAT_ID` проверяется в
`telegram/router.py` на каждое сообщение, все `settings` — глобальные
на весь бот, а не на пользователя. Чтобы пустить второго человека с
собственными настройками, потребуется:
- таблица пользователей с правами;
- все ключи `settings` (активный провайдер/модель/поиск и т.д.)
  переделать по образцу диалогов (`modules/conversations`) — с
  привязкой к `chat_id`, а не глобально;
- решить вопрос делимых лимитов (общие API-ключи = общий счётчик
  запросов и общий счёт);
- решить вопрос риска — например, доступ к `/pushcode`/`/editcode`
  от чужого имени в ваши репозитории.

Это отдельный шаг с отдельным обсуждением, не быстрая правка.

## Ветки диалогов (`modules/conversations/`)

Один `chat_id` может иметь несколько диалогов, у каждого своя история
и своя summary (`modules/memory/history.py`, `compactor.py` работают
по `conversation_id`, не по `chat_id`). Активный диалог на чат —
в `settings`. Самопамять (`self_memory`) — общая на все диалоги,
это то, что бот знает о себе/вас вообще, а не в рамках одной беседы.

Миграция для баз, созданных до этой возможности: старые сообщения и
summary автоматически переносятся в один "Перенесённый диалог" на
каждый `chat_id` при первом запуске нового кода — одноразово,
идемпотентно, ничего не теряется (`storage/db.py`:
`_backfill_conversations`).

## Поиск: retry и качество запроса

- **Retry на реальных ошибках** (`modules/search/service.py`) — один
  повтор через `SEARCH_RETRY_DELAY_SECONDS` (по умолчанию 2.5с),
  типичная причина — self-hosted SearxNG на Railway заснул
  (Serverless) и не ответил с первого раза. **Не** повторяется на
  `SearchConfigError` (нет ключа/URL) — такая ошибка не пройдёт и со
  второго раза.
- **Пустой результат ≠ ошибка.** Если поиск ничего не нашёл — бот
  честно отвечает "ничего не нашлось", **не** пробует автоматически
  другой провайдер. Осознанное решение: пустой результат часто
  означает, что в интернете действительно ничего релевантного нет;
  скрытый fallback добавил бы незаметные лишние запросы и мог бы
  маскировать проблемы конфигурации.
- **Уточнение запроса** (`llm/orchestrator.py`: `refine_query`) —
  отдельный лёгкий вызов LLM дочищает черновой запрос модели в
  компактный "поисковый" вид перед реальным поиском. Модель может
  запросить несколько разных запросов за один ответ (до
  `SEARCH_MAX_QUERIES_PER_TURN`) — что реально искалось, видно в
  ответе строкой `🔍 Искал: ...`.

## "Умное" определение бесплатных моделей (`llm/model_filter.py`)

Простая эвристика (`pricing.prompt == "0"`) не гарантированно
работает для всех провайдеров — например, у clavis.to цена может
лежать в нестандартном поле, для которого нет публичной документации
(риск повторить ошибку с Keenable). Вместо жёсткого парсинга под
каждого — компактные данные о цене (id + любые поля, похожие на цену
по названию) отдаются на анализ самой активной LLM, результат
кэшируется (`FREE_MODELS_CACHE_HOURS`). При сбое анализа — тихий
откат на эвристику.

## Дата и время в system-prompt

Вместо инструмента/round-trip'а (как для поиска) — текущие дата и
время (в `USER_TIMEZONE`) просто всегда подставляются в system-prompt
(`llm/prompts.py`) при каждом вызове. Это единственное значение,
которое сервер и так точно знает в момент запроса — незачем городить
отдельный механизм ради того, что можно отдать бесплатно и мгновенно.

## `/selftest` vs `tests/test_all.py`

Это два разных инструмента с разной целью:
- **`tests/test_all.py`** — юнит-тесты корректности кода, всё внешнее
  (Telegram, LLM, поиск, GitHub) намеренно замокано, реальные ключи
  не нужны. Не проверяет, работает ли реальный деплой.
- **`/selftest`** (`modules/diagnostics/service.py`) — живая проверка
  прямо на сервере: по одному минимальному настоящему вызову к
  каждому настроенному сервису, с текущими ключами. Показывает, что
  реально подключено и работает именно сейчас. Каждый запуск стоит
  немного реальных денег/лимитов — поэтому только вручную, не по
  расписанию.

## GitHub-навык: без клонирования репозитория

И `/pushcode` (Contents API, один файл — один коммит), и `/editcode`
(Git Data API: blob → tree → commit → обновление ref, несколько
файлов одним атомарным коммитом) работают только через GitHub REST
API — без `git clone` внутри контейнера, без временных файлов на
диске, без последующей очистки. `/editcode` читает текущее содержимое
файлов через тот же API, отдаёт модели, требует от неё **полное**
новое содержимое в строгом формате (`===FILE:===...===END===`) —
парсинг не зависит от того, какая именно модель отвечает.

Если ветка уже существует (продолжение правок несколькими вызовами
`/editcode`) — файлы читаются из неё же, а не из базовой, чтобы не
потерять предыдущие изменения.
