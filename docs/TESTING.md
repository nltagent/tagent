# Тесты

Два разных инструмента для разных целей — см. также
`docs/ARCHITECTURE.md#selftest-vs-teststest_allpy`.

## Юнит-тесты (`tests/test_all.py`)

Полный набор тестов на весь проект — только stdlib (`unittest` +
`unittest.mock`, без pytest). Реальные ключи и сеть не нужны — все
внешние вызовы (Telegram, LLM-провайдер, поиск, GitHub) подменены
моками. Каждый тест работает со своей временной SQLite-базой, ничего
не портит в вашей реальной.

Запуск:
```bash
cd tests && ./run_tests.sh
# или из корня:
./tests/run_tests.sh
# или руками:
PYTHONPATH=src python3 -m unittest tests.test_all -v
```

Что покрыто:
- заметки (CRUD, разграничение по chat_id);
- память агента (remember/forget, разбор тегов `[REMEMBER]`);
- история диалога и компактор (сжатие при превышении токен-бюджета,
  пропуск компакции при неудаче суммаризации);
- ветки диалогов (ленивое создание, переключение, закрытие с
  авто-созданием нового, изоляция истории/summary между диалогами,
  отклонение чужого/несуществующего id);
- миграция со старой схемы (сообщения и summary не теряются);
- парсер времени напоминаний (все форматы);
- напоминания (CRUD, выборка просроченных);
- мониторинг (`build_report` не падает и содержит нужные разделы);
- `scheduler.run_tick` (доставка напоминаний + троттлинг отчёта);
- оба провайдера поиска (ошибки при отсутствии ключа/URL,
  переключение, реальная форма запроса к SearxNG, retry на реальных
  сбоях и его отсутствие на ошибках конфигурации);
- LLM-клиент (форма запроса, retry по 429, логирование токенов);
- несколько профилей LLM-провайдеров (переключение, модель на
  профиль, реальный вызов уходит с нужными base_url/ключом);
- список моделей, простая эвристика и "умный" анализ бесплатных
  (включая нестандартное поле цены и откат при сбое LLM);
- system-prompt содержит текущие дату/время;
- оркестратор (обычный ответ, тег `[REMEMBER]`, цикл `[SEARCH]` с
  уточнением запроса, несколько запросов за раз, лимит на их число);
- GitHub-сервис (Contents API и атомарный Git Data API коммит на
  несколько файлов);
- редактор файлов через LLM (успех и ошибка при неполном ответе
  модели);
- `/selftest` (каждая проверка: OK, ошибка, пропущено);
- команды роутера целиком (`/start`, `/help`, `/note`, `/remind`,
  `/status`, `/setsearch`, `/setmodel`, `/models*`, диалоговые
  команды, провайдерные команды, обычный текст через LLM, отклонение
  "чужих" chat_id).

## Живая самопроверка (`/selftest`)

Команда в самом боте — не файл, не запускается руками из терминала.
Делает по одному минимальному настоящему вызову к каждому
настроенному сервису на реальном сервере, с текущими ключами. См.
`docs/ARCHITECTURE.md` за тем, чем это принципиально отличается от
юнит-тестов, и `docs/COMMANDS.md` за примером вывода.

## Правила при доработках

- Если меняется сигнатура функции, которую тестируют напрямую (не
  только через роутер) — обновить соответствующий тест в том же
  коммите/шаге, не откладывать.
- Тесты, которые монипатчат модульные функции напрямую
  (`orchestrator.chat_completion = ...` и т.п.), обязаны восстанавливать
  их — через `mock.patch.object(...)` (контекстный менеджер) или
  `patcher.start()` + `self.addCleanup(patcher.stop)`. Прямое
  присваивание без восстановления один раз уже приводило к утечке
  между тестами (см. `docs/HISTORY.md`, история про
  `search_service.search`) — новые тесты не должны повторять эту
  ошибку.
- После значимых изменений — прогнать набор не только один раз, но и
  в другом порядке классов (утечки между тестами не всегда
  проявляются в дефолтном порядке):
  ```bash
  PYTHONPATH=src python3 -m unittest tests.test_all.TestX tests.test_all.TestY -v
  ```
